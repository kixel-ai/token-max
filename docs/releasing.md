# Release preparation

token-max ships as the `token-max` crate on crates.io and as prebuilt
binaries on a GitHub Release with the same `v<version>` tag. Nothing is
published by a PR, tag, or merge. `Cargo.toml` is the only version source
and `--version` reports it.

The read-only `Check` workflow runs `just check` (formatting, clippy with
warnings as errors, the synthetic tests and `quest check`) on Linux, and the
tests on macOS and Windows. A change only to `quest/` and the agent docs
(`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`) runs `quest check` alone. The
required `Check` job aggregates them. A failed, cancelled, or skipped job
fails it, apart from the platform tests a quest-only change skips, so a
skipped draft run cannot satisfy the gate. PR jobs have no publication
credentials or OIDC permission.

## Binaries

[cargo-dist](https://github.com/axodotdev/cargo-dist), configured in
`dist-workspace.toml`, builds the release assets. The **Release** workflow is
written by hand rather than generated by `dist generate`, so that it keeps
the protected path below; it calls `dist build` for each target and once more
for the installers.

| Target | Runner |
| --- | --- |
| `x86_64-unknown-linux-musl` (static) | `ubuntu-24.04` |
| `aarch64-unknown-linux-musl` (static) | `ubuntu-24.04-arm` |
| `aarch64-apple-darwin` | `macos-15` |
| `x86_64-apple-darwin` | `macos-15` |
| `x86_64-pc-windows-msvc` | `windows-2025` |

Each release carries, per target, `token-max-<target>.tar.xz` (a
`token-max-<target>/` directory holding the binary, README and LICENSE) or,
on Windows, a flat `token-max-<target>.zip`, each with a `.sha256` file;
`token-max-installer.sh` and `token-max-installer.ps1`, which install into
the first of `$XDG_BIN_HOME`, `$XDG_DATA_HOME/../bin` and `~/.local/bin`; `source.tar.gz` with its `.sha256`; and `sha256.sum` over the archives. Every
asset gets a GitHub build provenance attestation, which
`gh attestation verify <file> --repo kixel-ai/token-max` checks.
`[package.metadata.binstall]` in `Cargo.toml` points `cargo binstall` at the
same archives.

The shell installer embeds each archive's checksum and refuses a mismatch,
but skips the check, saying so, on a system without `sha256sum`.
cargo-dist's PowerShell installer checks nothing. Where either applies,
verify the archive against `sha256.sum` or with `gh attestation verify`.

## max.kixel.me

`site/` is a Cloudflare Worker with only static assets and no code:
`index.html`, `style.css` and `site.js` are the landing page, `fonts/` holds
its two OFL fonts subset to Latin, `_redirects` sends `/install.sh` and
`/install.ps1` to the latest release's installers, and `run.sh` and `run.ps1`
are served as they are, so a release needs no deploy unless the page changes.
`_headers` allows scripts, styles and fonts from the page's own origin only.
`site.js` picks the Windows command on Windows, adds the copy button and plays
the terminal; without it the page still works and the terminal shows the whole
run. `tests/run_script.rs` runs the run script for the host (`run.ps1` on the
Windows CI job) against fixture releases on a local server.

The page is the maintainer's personal project: its header holds their avatar,
`avatar.webp` (their GitHub avatar at 96 pixels) linking to kixel.me, and
inline icons from
[Simple Icons](https://simpleicons.org) (CC0), since `_headers` allows only the
page's own origin.

The page's terminal is the maintainer's own `token-max doctor --defaults` over
the last 30 days across their hosts, run from `nixos` with `--ssh` for the
others, as HTML, with each host's EVERYTHING ELSE section cut to one line,
since that section is long and names project files that can belong to private
repositories. The results section below it comes from the same run's total and
two more runs on a terminal too wide to wrap a change's row, since a wrapped row
can't be parsed reliably: the same answers again, for each setting's saving on
the subscription, and every profile answered as API. The shown run gives the usage boxes
(the hosts' tokens, requests, and spend at API prices from `--since` to the run;
a spend with unpriced requests stops the script) and the saving on the
subscription, also in dollars at API rates. The API run gives the saving at API
rates and the breakdown by setting. Each line's bar is green for what the
wide run with the same answers saved on profiles not answered as API, and
violet for the rest; a line with no green is tagged "API only".
The subscription column is the shown run's total, as the maintainer pays, so
it includes what the profiles they answered as API save; the bars leave those
out. Doctor asks only how this host's profiles pay, so a destination's profiles
count as the subscription, and its main-agent cache TTL change stays "saves up
to". Billing picks only that change's default, and for a change to 1h "up to"
prices it against the API's 5m, so the second run counts it in full; a change
to 5m there stops the script, since only that profile's billing could price it.
The API column's percent adds the total's two rounded percents, so it can be
one point off; `docs/results.md` and the README's top are
an earlier, fuller replay and need not match it. After a change to doctor's
questions or output, run it again from the repository root on `nixos` after
`cargo build --release`, answering how each of its Claude profiles pays
(doctor asks only about this host's), and adding `--ssh kixtop` when the laptop
is online:

```sh
python3 assets/demo/site.py site/public ~/.claude=p ~/.claude-api-credits=a ~/.claude-personal.merged-20261106=a \
  --since "$(date -u -d '29 days ago' +%F)" --ssh desktop --ssh fedora --include-local
```

It writes the run and the results into `index.html`, and the run's timing and the breakdown's bars into `style.css`. Read the
result before committing it: it is public, so it must name no private
repository, customer or project. The README's recording, `assets/demo/walk.gif`,
runs on synthetic transcripts instead, and `assets/demo/walk.tape`
regenerates it. `og.png`, the link preview, is a 1200x630 screenshot of the
page's top, from the logo through the run box; retake it after changing that
part. The run box ends below 630 pixels at a 1200-pixel width, so take it at a
1280x672 viewport with a device scale factor of 0.9375 (`agent-browser set
viewport 1280 672 0.9375`), in a headless browser: the agent Chrome's screenshots
time out.

Preview the page, its headers and redirects locally with
`nix shell nixpkgs#wrangler -c wrangler dev` from `site/`. After changing
`site/`, deploy by hand from that directory with a wrangler login for the
Cloudflare account that holds both kixel.me and kixel.ai:

```sh
nix shell nixpkgs#wrangler -c wrangler deploy
```

max.kixel.ai, the page's first host, answers every path with a 301 to the same
path and query on max.kixel.me, so shared `/install.sh` and `/run.sh` links keep
working. `site/redirect/` is that Worker, named `max-kixel-ai` like the
assets-only Worker it replaced; deploy it the same way from its directory, only
when it changes.

The flake's default package builds from source and needs no release:
`nix run github:kixel-ai/token-max -- doctor`.

To upgrade cargo-dist, change `cargo-dist-version` in `dist-workspace.toml`
and `DIST_VERSION` in `release.yml`, and replace every pinned SHA-256 in
`release.yml` (each matrix `dist-sha256` and the `installers` job's
`sha256`) with the matching line of that release's `sha256.sum`.

## Release setup

Two GitHub environments hold the release's write access, each restricted to
**only the branch `main`**:

- `github-releases` creates and publishes the GitHub Release
  (`contents: write`, plus attestations). It holds no secrets.
- `crates-io` publishes the crate. Publication credentials live only in this
  environment, never in repository secrets, PR jobs, or checkout files.

crates.io creates a trusted publisher only for a crate that already exists,
so the first release publishes with a token:

1. For the first release, create a short-lived crates.io API token with the
   `publish-new` scope, store it as the `crates-io` environment secret
   `CARGO_BOOTSTRAP_TOKEN`, and dispatch with `bootstrap`. Revoke the token
   and delete the secret afterwards.
2. Then add a trusted publisher on the crate's crates.io settings for owner
   `kixel-ai`, repository `token-max`, workflow `release.yml` and
   environment `crates-io`. Later releases use the default `trusted` mode,
   where `rust-lang/crates-io-auth-action` exchanges the job's OIDC token
   for a temporary publish token and revokes it when the job ends.

An agent can drive Chrome through crates.io owner setup when requested; login
and crate ownership still belong to the owner. Do not send credentials in chat.

## Publish

A release's PR sets its version in `Cargo.toml` and `Cargo.lock` through the protected,
reviewed squash path, after running `token-max doctor` end to end on a real
host. Redeploy the site once the release is public if that PR changed
`site/`.

Dispatch **Release** on protected `main` with that exact version. Preflight
refuses 0.0.0, a prerelease (the release is always marked latest, which the
installers serve), a mismatched version, and a version crates.io already
has. `draft` refuses an existing tag on another commit. Then, in order:

1. The complete Check workflow and every target's build run.
2. The installers and `sha256.sum` are built from all the archives.
3. `draft` attests every asset and uploads it to a draft release, which is
   not public and creates no tag. Until `publish` succeeds, a retry, even
   from a later commit, reuses the draft and moves it to the new commit.
4. `publish` runs `cargo publish --locked` from the restricted environment.
5. `announce` publishes the draft as the latest release, which creates the
   tag at the dispatched commit.

A failure before step 4 leaves nothing public. crates.io cannot be undone,
so it goes after everything that can fail is staged; if `announce` fails,
rerun it in the same run, since preflight refuses a new run for a version
crates.io has. Inspect the package first with `cargo publish --locked --dry-run`
and `cargo package --list`.

To check a change to the release itself, dispatch **Release** from its
branch with `dry-run` and the branch's `Cargo.toml` version (0.0.0 is
allowed). It builds every archive and installer and uploads them as workflow
artifacts; the jobs that publish only run on `main` without `dry-run`.

After publication, run both installers through max.kixel.me, and both run
scripts, from a clean home without a Rust
toolchain, and `cargo binstall token-max` and `cargo install --locked
token-max` from a clean `CARGO_HOME`; verify help, version and a synthetic
priced analysis for each. A failed publish is a release failure, never permission to
publish an incomplete placeholder.

Sources checked 2026-11-08: [crates.io trusted publishing RFC 3691](https://rust-lang.github.io/rfcs/3691-trusted-publishing-cratesio.html),
[crates-io-auth-action](https://github.com/rust-lang/crates-io-auth-action), and
[GitHub environment protection](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

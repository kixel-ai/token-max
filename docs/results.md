# Results on the maintainer's machines

The README and [max.kixel.ai](https://max.kixel.ai) lead with figures from
`token-max doctor --details --since 2026-10-19T11:59:22Z` and the same with
`--defaults`, run 2026-11-18 on each of the maintainer's four machines, a macOS
laptop and three Linux hosts, from commit `aeb01f5` (main with the shared
settings fix, before the auto-compact percent override). They are a dated
snapshot, regenerated by hand; change all three together. Names of the
maintainer's private skills, MCP servers and paths are left out, and no prompt
or reply text is published.

## Totals

Each machine ran doctor on its own, since doctor asks how a profile pays only
on its own host, so these totals are its four reports added by hand, as
`doctor --ssh` adds hosts:

| Machine | Requests | Sessions | API cost | Potential savings |
| --- | --- | --- | --- | --- |
| Laptop (macOS) | 29,786 | 203 | ~$2,279 ± $14 | ~$390/mo, margin unknown |
| Workstation | 757,404 | 7,124 | ~$44,093 ± $67 | ~$3,215/mo ± $33 |
| Server | 205,384 | 2,032 | ~$13,022 ± $131 | ~$789/mo ± $4 |
| Second workstation | 197,819 | 2,817 | ~$11,114 ± $5.33 | ~$1,259/mo ± $3.49 |
| **All four** | **1,190,393** | **12,176** | **~$70,508 ± $148** | **~$5,653/mo, margin unknown** |

- **API cost** is every recorded Claude Code, Codex and T3 Code request at
  public API prices, extrapolated over the requests that could not be priced
  (`~`, with a 95% margin). The total's margin combines the machines' in
  quadrature, as doctor combines profiles. The machines are summed as they
  are: a history copied from one to another would count on both.
- **Sessions** count each Claude Code session and Codex thread once, with the
  subagents and review threads it spawned.
- **Potential savings** is the line under each `--defaults` report's
  headline: what every change doctor would make for a user with no settings
  files saves at the window's rate, recommended and worth considering alike,
  8% of the spend. 7 more changes, such as Codex's effort, could not be
  measured. Each saving holds the other settings constant, so overlapping
  changes may save less. The laptop's margin is unknown because one of its
  savings came from too few priced requests to measure a spread. ~$3,940/mo is
  a 1h subagent cache on the plan profiles, and ~$518/mo a 1h main-agent cache
  on the usage credits profiles, both Measured lines. ~$391/mo is turning auto
  memory off, the maintainer's Opinion line. The remaining ~$804/mo is skills
  and built-in tools that were never used or cost more than $1 per use, led by
  the Workflow tool, the ScheduleWakeup tool, the `dataviz` skill and the
  `code-review` skill.

Against the maintainer's current settings, the changes doctor still offers save
~$781/mo. Their settings already save ~$4,452/mo against the defaults, as each
report's "Compared with defaults" line gives it: the 1h caches the plan
profiles set, less the small cost of the 1h subagent cache on the usage
credits profiles. Each figure adds up changes measured one at a time against
a different baseline, so together they need not equal the ~$5,653/mo above.

doctor asked how each Claude profile pays, and the maintainer answered from
the profile's account (`oauthAccount.billingType` in its `.claude.json`): every
machine's `~/.claude` is on a plan, and the usage credits profiles, plus an
archived profile with no account, were answered as API. Every offered change
was declined, and no settings file changed.

## Prompt cache TTL

Replays of the same sessions at 5m and 1h, summed over the four machines. Each
is a Measured line in its profile's `settings.json`; the cost is the cache's
over the window.

| Setting | Profiles | 5m | 1h | 1h against 5m |
| --- | --- | --- | --- | --- |
| `subagentPromptCacheTtl` | plan; `--defaults` baseline unset (5m) | ~$23,878 | ~$19,929 | ~17% less, ~$3,950 ± $29 |
| `promptCacheTtl` (main agent) | usage credits; `--defaults` baseline unset (5m) | ~$1,393 | ~$874 | ~37% less, ~$519 ± $2.08 |

The plan profiles' subagent line is now priced, so its ~$3,940/mo is in the
savings above. The previous snapshot left it out as "not enough evidence": T3
Code shares those profiles' histories, and doctor could not tell whether a T3
session ran under the profile's setting. It now reads the shared settings file
for the controls T3 leaves alone. [T3 Code](reference.md#t3-code)
describes the rule. On the usage credits profiles, whose main agent gets 5m
unless set, 1h is the ~$518/mo in the savings; on their few subagent requests
5m was cheaper, by ~$3.63 over the window.

Compared with the 2026-11-17 snapshot (`a90ee51`, window from 2026-10-18),
requests rose 0.7% and the cost 0.7%, and the savings rose from ~$1,689 to
~$5,653/mo, almost all of it the subagent cache. The maintainer's plan
profiles now set `subagentPromptCacheTtl` to 1h, so the report against their
current settings no longer offers it.


## Against T3 Code's count

This section is the 2026-11-17 snapshot's (`a90ee51`, window from
2026-10-18) and was not retaken: the T3 Code figures below were read that day,
so a comparison against a later window would mean nothing. Its method still
holds.

T3 Code's usage page showed **$60,391.31 over 23,285 sessions** for its last
30 days, as an API estimate, read the same day. `token-max sessions`, run on
each machine over that window, accounts for most of the difference:

- **Sessions.** T3 Code counts every transcript's session ID and every Codex
  rollout, so a Codex subagent or review thread is a session of its own. The
  export lists each session and subagent on its own line: 23,250 across the
  four machines, within 0.2% of T3 Code's count. doctor counts a subagent with
  the session that spawned it, which gives 12,076; the export's lines without a
  parent, plus the parents that ran before the window, agree with it exactly on
  two machines, within 3 sessions on the second workstation and within 3% on
  the server.
- **Cost.** T3 Code adds $0 for a request it cannot price; doctor extrapolates
  over them. The export's priced requests alone come to $65,375, 8% above
  T3 Code. The rest is how each prices and windows: T3 Code prices from
  LiteLLM's table and doctor from models.dev, and T3 Code's 30 days are local
  calendar days ending when it was read, several hours before these runs
  ended.

Neither is an invoice: on a plan, both measure what the usage would cost at
API prices.
